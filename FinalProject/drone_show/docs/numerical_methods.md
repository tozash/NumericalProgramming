# Numerical Methods (TA Appendix)

This document summarizes the numerical method used in this project and the key accuracy/stability properties required by the Final Project rubric.

## Classical RK4 (Runge–Kutta 4)

We integrate the swarm dynamics ODE (an IVP) using the **classical explicit RK4** method with a fixed time step \(h=\Delta t\).

### Butcher Tableau (RK4)

| \(c\) | \(a_1\) | \(a_2\) | \(a_3\) | \(a_4\) |
|---:|---:|---:|---:|---:|
| 0   | 0   | 0   | 0   | 0   |
| 1/2 | 1/2 | 0   | 0   | 0   |
| 1/2 | 0   | 1/2 | 0   | 0   |
| 1   | 0   | 0   | 1   | 0   |
|     | 1/6 | 1/3 | 1/3 | 1/6 |

In code, this corresponds to:

\[
\begin{aligned}
k_1 &= f(t_n, y_n)\\
k_2 &= f(t_n + h/2,\, y_n + (h/2)k_1)\\
k_3 &= f(t_n + h/2,\, y_n + (h/2)k_2)\\
k_4 &= f(t_n + h,\, y_n + hk_3)\\
y_{n+1} &= y_n + \frac{h}{6}\left(k_1 + 2k_2 + 2k_3 + k_4\right).
\end{aligned}
\]

## Truncation Error (Brief, Correct)

Assuming \(f\) is sufficiently smooth:

- **Local truncation error (LTE)** of RK4 is \(O(h^5)\).  
  Intuition: RK4 matches the Taylor expansion of the true solution through terms of order \(h^4\), so the first omitted term is order \(h^5\).

- **Global (accumulated) error** over a fixed time interval is \(O(h^4)\).  
  Intuition: over \(N \approx T/h\) steps, the \(O(h^5)\) per-step error accumulates to \(O(Nh^5)=O(h^4)\).

This is why decreasing \(\Delta t\) typically reduces the final formation error, until floating-point limits or model/parameter limits dominate.

## Stability Notes (Including A-stability)

### What is A-stability?

A one-step method is **A-stable** if it is stable for the linear test equation

\[
y' = \lambda y,\quad \mathrm{Re}(\lambda) < 0
\]

for **any** step size \(h>0\). Informally: for all decaying linear systems, the numerical method does not introduce artificial growth regardless of \(h\).

### Is RK4 A-stable?

No. The **classical explicit RK4 is not A-stable**: for sufficiently stiff problems (large negative \(\lambda\)), large \(h\) can lead to instability.

### Why is our project stable in practice?

Even though RK4 is not A-stable, our simulations are stable in typical runs because:

- **Damping is present**: the dynamics include a \(-k_d v\) term, which reduces oscillations and helps keep trajectories bounded.
- **Forces are bounded by modeling choices**:
  - repulsion only activates inside a safety radius \(R_{\text{safe}}\)
  - velocity is saturated to \(v_{\max}\) (see `src/drone_show/dynamics.py`)
- **We choose \(\Delta t\) conservatively**:
  - empirically, too-large \(\Delta t\) produces visible instability / non-convergence (see failure demonstration `outputs/failures/case1_dt_too_large/` generated by `scripts/run_failure_cases.py`)
  - we also include a helper for dt studies: `src/drone_show/analysis.py::dt_refinement(...)`, which runs the same task over a list of dt values and records error vs runtime.

In short: we avoid the stiff regime where explicit RK4 would require extremely small steps, and we use damping + saturation + dt selection to maintain stability in the operating range used for the drone-show tasks.
